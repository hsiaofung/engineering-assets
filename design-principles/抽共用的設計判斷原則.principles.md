# 共用的是穩定的責任，不是「看起來很像」的程式碼。

----

對。這樣比較準確：**不要把「抽不抽」當成規則，而是把規則拿來輔助 Design Judgment。**

我會把「抽共用」的判斷整理成下面這套。

### 抽共用的設計判斷原則

| 判斷                   | 問題                                            | 傾向         |
| -------------------- | --------------------------------------------- | ---------- |
| **Responsibility**   | 兩個地方是不是在做同一個責任？                               | 同責任 → 考慮抽  |
| **Behavior**         | 行為是否真的一致，而不只是程式碼長得像？                          | 一致 → 考慮抽   |
| **Change reason**    | 未來會不會因為不同需求而各自修改？                             | 不同 → 不要抽   |
| **Variation**        | 差異是不是少數幾個穩定的參數？                               | 是 → 可以抽    |
| **Coupling**         | 抽出後會不會讓 parent/child 產生很多 Input/Output/DI 關係？ | 越複雜 → 越不該抽 |
| **Abstraction cost** | 抽出後是否比 duplication 更容易理解？                     | 否 → 不抽     |
| **Reuse**            | 現在或可預見的未來是否真的有多個使用者？                          | 沒有 → 不急    |
| **Stability**        | 共用的部分是否已經穩定？                                  | 不穩定 → 先不要抽 |
| **Domain meaning**   | 抽出的東西是否有清楚的 domain 意義？                        | 有 → 比較值得抽  |
| **Maintenance**      | 未來修改一次是否真的能因此減少維護成本？                          | 能 → 值得抽    |

---

### 最重要的三個判斷

如果要簡化成我實際做 Design Review 時會問的三個問題：

**① 它是不是同一個 Responsibility？**

不是「都有 table」，而是：

> 「它們是不是負責同一件事情？」

---

**② 它們未來是不是會因為同一個原因改變？**

這個其實非常重要。

例如：

```text
Processor
Memory
Storage
Network
```

雖然都有：

```text
DataLoader
→ DataTable
→ pagination
→ sort
→ filter
```

但它們的 columns、API、資料結構、業務需求都可能不同。

所以：

> **現在看起來很像 ≠ 未來應該一起改。**

---

**③ 抽出來之後，複雜度有沒有下降？**

這是最後一道防線。

例如為了抽：

```text
ComputeResourceList
```

結果變成：

```text
ComputeSystemsPage
    ↓ Input
ComputeResourceList
    ↓ inject
DataLoader
    ↓ Output
selection
    ↓
tableState
```

如果最後需要很多：

```ts
@Input()
@Output()
inject(...)
ViewChild(...)
```

才能把原本簡單的 Page 拆開，

那就代表：

> **我們只是把 duplication 換成 coupling。**

這種情況寧願保留 duplication。

---

## 所以套回現在的 Compute

我會做這個 Design Judgment：

### `DataTableV1`

**抽。**

因為它的 responsibility 非常清楚：

> Table UI + table interaction

---

### `DataLoader`

**抽。**

因為 responsibility 也很清楚：

> Data fetching lifecycle

而且已經有穩定 API：

```ts
[getFn]
data()
isLoading()
error()
refresh()
```

---

### `ComputeResourceList`

**目前不抽。**

不是因為「不能抽」，而是目前證據不足。

Systems Page：

```text
查 Systems
+ System List
```

Drawer Page：

```text
查 Drawer 的 Systems
+ System List
+ Drawer Detail
```

雖然中間有一段相似，但兩個 Page 的**整體 responsibility 不同**。

而且目前只有兩個 case。

所以現在：

```text
copy
→ modify
→ test
→ observe duplication
→ 再決定是否抽
```

反而是比較好的 Design。

---

我會把這個原則濃縮成一句你以後做設計時很好用的話：

> **不要因為「程式碼很像」就抽；要因為「責任相同、變更原因相同，而且抽出後複雜度真的下降」才抽。**

這個其實比單純的 **DRY** 更適合拿來做 architecture / component design 的判斷。
